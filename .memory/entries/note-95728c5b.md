User's position: the simulator is built so what's written is correct; overwriting a function should naturally drop confidence, but modular additions should not erase what we already know.

Agreed, conditional on factoring knowledge by function (edges pinned to code). Additions add edges and leave existing ones intact; a monolithic surrogate would need retraining on every change. This is an argument FOR function-level factoring.

Three exceptions to design for:
1. Input-distribution shift: an addition (e.g. ASCE 7 lateral loads) feeds an unchanged edge (e.g. column sizer) inputs outside its tested range. Knowledge is not wrong but extrapolating. Track two separate flags per edge: function changed vs inputs out of distribution.
2. Routing change: a new system option or changed DesignParameters default sends existing designs down a different branch. Per-edge knowledge holds; multi-edge path conclusions (e.g. fc -> punching worsens) need re-check.
3. Bug fixes are overwrites and should invalidate (we learned the buggy behavior). Invalidation must follow the call graph (transitive callees / shared helpers), not just the file.

Rule: an edge loses confidence when its function or any callee changes; gets an extrapolation flag when inputs drift; cross-edge path conclusions are re-verified on routing changes. The memory `codebase` blast/callees actions give most of the call-graph closure.

Evaluation asset: replay menegroth's git history (learn on an old version, apply real commits, measure correctly-retained vs wrongly-retained knowledge).
