## Finding (adversarial critic, crit2 of run-e5fed01c; VERIFIED by direct read)
:column_I_factor and :beam_I_factor are TOP-LEVEL DesignParameters fields (design_types.jl:515-516) but are registered in NONE of the incremental engine's 3 invalidation surfaces:
- PREPARE_AFFECTING_FIELDS (scheduler.jl:85-90) — absent
- NODE_SLAB_SIZING.param_slice (provenance.jl:150-152) — absent
- NODE_MEMBERS.param_slice (provenance.jl:171-174) — absent

## Impact (safety-critical, DEFAULT production path)
SS_API_INCREMENTAL defaults true (cache.jl:70). `redesign(session; column_I_factor=0.50)` or POST /design with a factor-only change: changed_param_fields=[:column_I_factor]; intersect with PREPARE_AFFECTING_FIELDS = ∅ → treated as a legal incremental redesign (no throw); no node param_slice contains the field → dirty_frontier=∅ → full memo hit → the base design is returned UNCHANGED at 0.70. User gets HTTP 200 with a design computed at the wrong cracked stiffness, no warning. Cold design_building path is correct; the stateful engine that drives the API is not.

## Pre-existing, not introduced by Change 0/1
The cold-path threading (Change 0 frame, Change 1 flat-plate) is correct; the gap is that the knobs were never wired into the incremental metadata. Relates to pre-existing todo-cd4f1ef8 (DesignParameters field-completeness invariant / dead beam_I_factor).

## Chosen fix (coarse = only fully-correct option)
Add :column_I_factor AND :beam_I_factor to PREPARE_AFFECTING_FIELDS. Rationale: slab column stubs are BAKED at prepare! time (_apply_col_I_factor in _process_single_slab_group, utils.jl:681), so only a fresh prepare picks up a changed factor; the finer per-node param_slice approach would recompute nodes but leave the baked stubs stale. Forcing a fresh prepare also resolves the P1 live-vs-baked lifecycle split (_reconcile_columns! reads it live at design_workflow.jl:911). Matches the file's own classification philosophy (prepare-affecting vs node-slice).

## Also folding in (P2a)
Loosen the new col_I_factor::Float64 kwargs to ::Real for consistency with the sibling I_factor::Real convention (members/utils.jl:2491); _apply_col_I_factor already does Float64(factor).
