Two design decisions confirmed with the user on the T-beam capacity cache:

1. NO cross-session disk persistence. Capacity values are code-derived (ACI φMn/φVn/εt). An in-memory cache self-invalidates on process restart, so it can never serve capacities from stale code. A disk cache would silently serve stale/unconservative capacities if any function feeding precompute_capacities! changes — a safety-critical hazard for marginal benefit (cross-session reuse only hits on IDENTICAL rib geometry; different buildings → different keys → no hit). The within-design reuse (~20 iterations, the −41% sbc_mip win) is already captured in-memory via the per-struc WeakKeyDict store. If a repeated-identical-geometry workflow ever needs persistence, the ONLY safe form is a manually-bumped CAPACITY_SCHEMA_VERSION in the key — deferred (discipline burden).

2. Keep CONTENT-keyed catalog, do NOT eliminate the per-call catalog rebuild. optimize_discrete needs the real RCTBeamSection structs, so a cache hit still rebuilds the (lightweight) catalog. Avoiding the rebuild requires INPUT-based keying (hash flange-fn evaluated at the builders' web widths), which couples the key to catalog-builder internals — a drift between key and real catalog is a silent-staleness hazard. The rebuild is second-order vs the precompute; robustness of content-keying (key = the actual built catalog) is worth more than a few seconds. Revisit only with measurement if it becomes a real bottleneck.
