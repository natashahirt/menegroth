Design note: docs/sizing-map/rigidlink-factorization-cache.md.

FINDING: Asap already reuses the CHOLMOD symbolic analysis for the NON-link path (_get_factorization -> cholesky! in-place on values_only updates, guarded by _factor_pattern_key + _factorization_stale). The rigid-link path (solve!(model,links), solve(model,cases,links)) bypasses it entirely and does a fresh cholesky(Krr) EVERY call (44/48 building factorizations: walls 28, members 16), then nulls model._factorization.

KEY INSIGHT: on a value-only re-solve (section changed, mesh/links/geometry unchanged) G, dependent, retained_free, and the Krr SPARSITY PATTERN are invariant; only Krr values change => reuse symbolic via cholesky!.

PHASE 1 (mutating solve! path, no Model struct change): reuse the model's existing _factorization/_factorization_stale/_factor_key slots for the REDUCED factor (the link path already nulls them, and no-link _get_factorization is never called on a link model because _solve_struc_model! branches on isempty(links)). New helper _get_reduced_factorization!(model, Krr, retained_free) mirrors _get_factorization with a REDUCED pattern key = hash((objectid(model.S), nnz(model.S), retained_free, Krr.data.colptr, Krr.data.rowval)). Fast path (not stale, key match) reuse; refactor path (stale, key match) cholesky!(old,Krr); else fresh cholesky + LDLt + LU fallback = today's behavior. solve! KEEPS the reduced factor instead of nulling. Lifecycle driven by existing update!(values_only) -> _invalidate_factor_values! (stale) and full update!/process! (null).

EXACT-OR-DOESNT-FIRE: every reuse guarded by the key + staleness; any mismatch/non-SPD => fresh cholesky. Never a wrong displacement; worst case no speedup.

PHASE 2 (deferred): non-mutating solve(model,cases,links) must not write model state; already reuses one factor across cases within a call; cross-call needs an external RigidLinkFactorCache handle on BuildingStructure. Deferred.

VERIFY: Asap rigid-link + factorization-cache suites; core-office design cache-on vs forced-fresh byte-identical; member-stage 299 bit-identical.
