## GOTCHA (reusable) — singleton member groups defeat `group_id`-based introspection
The first gate run FAILED at '✓ found a representative CONCRETE beam element'. Root cause: the helper filtered with `gid = SS.group_id(m); gid === nothing && continue`, but in the vault fixture **ungrouped beams are SINGLETON member groups where `group_id(m) === nothing`** — group ids exist only as keys in `struc.member_groups`, not on the members. So every beam was skipped.

**Fix pattern:** locate elements by **section type** via `struc.member_groups`, not `group_id`:
- beam group ⇔ `mg.section isa RCBeamSection || RCTBeamSection`; column group ⇔ `mg.section isa RCColumnSection || RCCircularSection`.
- then `mg.member_indices` → correct member array (`struc.beams`/`struc.columns`) → `SS.segment_indices(m)` → `struc.segments[seg].edge_idx` → `struc.asap_model.elements[edge_idx]` (mirrors `_apply_beam_results!`/`_apply_column_results!`).
- **Caveat:** `build_member_groups!` empties+repopulates the single `struc.member_groups` dict per member type each sizing pass, so after a beam→column workflow it holds only column groups, and the rebuild clears `mg.section`. Read the chosen section from the representative member (`SS.section(m)` → `m.base.section`, which persists) and rebuild the group map for the requested `member_type` before scanning.
