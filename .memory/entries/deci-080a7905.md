Both follow-ups filed after Phase 11 are resolved in a single session (2026-07-16).

**Follow-up 1 — Sparse joists on multi-bay grids (`p11-followup-2x2-sparse`).**
`_slab_boundary_edges` used `edge_face_count(skel, e) == 1` — a WHOLE-FLOOR-PERIMETER test — which stripped every interior girder shared between adjacent slabs. For a per-bay slab in a multi-bay layout this reduced to: corner bay = 2 boundary edges, edge bay = 1, interior bay = 0 (fallback to all face edges). Joist lines could not find 2 intersections, so:
  * 3×3 medium-office grid, 24" spacing → 7 joists total (only the interior bay produced any)
  * 2×2 medium-office grid, 24" spacing → 0 joists total

Fix: rewrite `_slab_boundary_edges` to use the correct topological definition — an edge is a slab boundary iff exactly ONE of the slab's own faces contains it. Multi-cell slabs' shared interior edges are excluded; girders shared with an adjacent slab are included (they ARE this slab's perimeter). After fix: 3×3 → 63 joists (7/slab × 9), 2×2 → 40 joists (10/slab × 4), uniformly across every bay.

**Cascade: exposed a pre-existing gap in `_compute_inward_normal`.** With per-slab boundaries, joist landings now fall on outer-perimeter edges (efc=1). `_split_host_edge!` rewires those edges (v1, v2) → (v1, mid1) and adds new sub-edges, but does NOT update `face_vertex_indices` / `face_edge_indices`. Downstream `update_structural_offsets!` on corner columns then called `_compute_inward_normal(v_col, mid_landing, edge)` which walked the face's CCW vertex list for a consecutive (v_col, mid_landing) pair — but only the ORIGINAL corners are in that list. Added a colinearity-fallback: since the landing lies on the same line as the original edge, we recover the CCW direction by finding the face's original grid-corner neighbor of `v_col` that is colinear with the sub-edge and using ITS CCW pair. This is a localized, geometry-based fallback — the deeper fix (making `_split_host_edge!` maintain face topology) is a separate architectural change tracked by `todo-e903a5ae`.

**Follow-up 2 — RC beam volume-dict key inconsistency (`p11-followup-volume-key`).**
5 sites in `analyze/members/utils.jl` used `material.concrete` (Concrete key) for `MaterialVolumes` when `material isa ReinforcedConcreteMaterial`; 3 sites in the NLP concrete-beam path used `material` (RC key) directly. `element_ec(volumes)` in `postprocess/ec.jl:76` reads `mat.ρ` — ReinforcedConcreteMaterial has no `ρ` field, so the NLP path would break embodied-carbon computation.

Fix: centralize the material-unwrap into a `_volume_key(material)` helper in `building_types/cells.jl` (RC → `mat.concrete`, else pass-through). Apply at all 6+3 sites + the framing populate initialization site. Removes the dead `mat_vols_base = ... never used` in `_apply_beam_results!` as a bonus.
